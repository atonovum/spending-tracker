# 동기화

이 앱의 저장소는 두 개다.

| | 무엇 | 성격 |
|---|---|---|
| **로컬** | 브라우저 localStorage (`spending-tracker-v5`) | 1차 저장소. 앱은 이것만으로 완전히 동작한다 |
| **캐시** | Cloudflare Worker KV, 키 하나 (`state`) | 기기 사이를 잇는 유일한 다리 |

KV는 "캐시"라 부르지만 **없어도 되는 사본이 아니다.** 폰과 노트북이 같은 데이터를 보는 경로가 이것뿐이므로, 지워지면 다른 기기의 변경을 받을 방법이 없다.

문서는 **통째로** 오간다. KV에는 지갑·카테고리·레이블이 전부 담긴 키가 하나 있을 뿐이고, 지갑 단위나 거래 단위로 주고받는 경로는 없다. 그래서 충돌 해소도 문서 단위다 — 병합이 아니라 한쪽이 이긴다.

**두 방향은 대칭이 아니다.** 로컬 → 캐시는 저절로 일어나고, 캐시 → 로컬은 상황에 따라 다르며 수동 경로가 따로 있다.

---

## 1. 로컬 → 캐시 (푸시)

### 언제

**거래가 바뀔 때마다 자동으로.** 사용자가 누를 버튼은 없다.

| 계기 | 시점 |
|---|---|
| 거래 추가·편집·삭제, 카테고리/레이블/지갑 변경, CSV·JSON 가져오기 | 마지막 변경으로부터 **800ms 뒤** |
| 앱이 백그라운드로 갈 때 (`pagehide`, 탭 숨김) | **즉시** — 대기 중인 푸시를 흘려보낸다 |
| 네트워크 복귀 (`online`) | 즉시 |
| 실패 후 재시도 | 2초 → 5초 → 15초 → 60초 (이후 60초 고정) |

800ms는 디바운스다. 연속 입력하면 타이머가 매번 다시 시작한다.

백그라운드 flush가 따로 있는 이유: **iOS는 백그라운드로 넘어간 홈 화면 웹앱을 즉시 얼린다.** 아직 안 터진 타이머는 영영 안 터지므로, 나가는 길목이 마지막 기회다. 이때는 `fetch(..., { keepalive: true })`로 보내 페이지가 사라져도 요청이 살아남게 한다. (`sendBeacon`은 `If-Match`를 실을 수 없어 못 쓴다.)

### 어떻게

PUT은 `If-Match: <마지막으로 아는 리비전>`을 실어 보낸다. 리비전은 문서 안의 `updatedAt`(epoch ms)이고, Worker가 이를 `ETag` 헤더로 돌려준다. 서버가 자기 리비전과 대조해 다르면 409를 준다 — 그 사이 다른 기기가 쓴 것을 덮지 않기 위한 장치다.

### 결과별 동작

| 응답 | 동작 |
|---|---|
| 성공 | 새 리비전을 로컬 문서에 되찍고 **미전송 플래그 해제** |
| 409 충돌 | 서버 문서를 다시 읽어 채택 + 토스트. 읽기까지 실패하면 그렇게 말하고 재시도 |
| 413 너무 큼 | 토스트. **재시도하지 않는다** — 페이로드는 저절로 줄지 않는다 |
| 인증 만료 | 토스트(자동으로 안 닫힘). 플래그 유지, 재시도는 계속 — 다시 로그인하면 앱을 다시 열지 않아도 그 자리에서 올라간다 |
| 그 외 실패 | 플래그 유지, 백오프 재시도 |

### 미전송 플래그

`spending-tracker-pending-sync` — 이 기기가 서버에 확인받지 못한 변경을 들고 있다는 표시다. Settings의 동기화 배지가 이 값을 보여준다(🟡 미전송 / 🟢 동기화됨).

**`updatedAt`만으로는 이 사실을 알 수 없어서 존재한다.** `updatedAt`은 서버가 푸시를 확인해줄 때만 전진하므로, 푸시가 실패한 기기는 내용은 앞서 있으면서 리비전은 서버의 옛 값을 그대로 든다. 리비전만 비교하면 낡은 서버가 이겨서 편집분이 조용히 사라진다 — 실제로 이렇게 잃었다.

이 플래그는 기기마다 다른 값이고 문서 밖에 산다. CSV·JSON 내보내기에도, KV 페이로드에도 들어가지 않는다.

## 2. 캐시 → 로컬 (풀)

### 자동 — 시작할 때와 돌아올 때

| 계기 | 조건 |
|---|---|
| 앱 최초 로드 | 항상 |
| 포그라운드 복귀 (`visibilitychange` → visible) | 마지막 읽기로부터 5초 경과 시 |
| Safari가 bfcache에서 페이지 복원 (`pageshow`, `persisted`) | 위와 같음 |
| 네트워크 복귀 (`online`) | 위와 같음 |

**주기적 폴링은 없다.** 타이머가 도는 곳이 하나도 없고, 위 계기가 올 때만 한 번 읽는다. 5초는 주기가 아니라 **최소 간격**이다 — 데스크톱에서 탭을 옮길 때마다 이 이벤트가 뜨므로, 없으면 새 정보도 없는 요청이 몇 초마다 나간다.

복귀 때마다 읽는 이유: **iOS 홈 화면 웹앱은 다시 열어도 재로드가 아니라 재개다.** 얼려둔 페이지가 React 트리째 깨어나므로 최초 로드 시의 읽기가 두 번 다시 돌지 않는다. 마운트에서만 읽으면 앱을 몇 번을 다시 열어도 며칠 전 문서를 계속 보여준다.

### 자동 경로의 판정

읽고 나서 누가 이길지 정한다. 위에서부터 먼저 맞는 규칙이 이긴다.

| 조건 | 결과 |
|---|---|
| 서버가 응답하지 않음 | **아무것도 안 함** |
| 이 기기에 미전송 변경이 있음 | 로컬을 **올림** |
| 서버가 비어 있음 | 로컬을 올림 |
| 로컬 리비전 > 서버 리비전 | 로컬을 올림 |
| 그 외 | 서버 문서를 **채택** |

"서버가 응답하지 않음"과 "서버가 비어 있음"은 다르게 다룬다. 빈 서버는 로컬로 채우면 되지만, 못 닿는 서버에 푸시하면 `If-Match` 없이 나가서 읽어본 적 없는 리비전을 덮어쓴다.

미전송 변경이 리비전 비교보다 **먼저** 온다. 사용자가 아무 의사표시도 하지 않은 자동 경로에서, 낡은 서버가 아직 못 올린 편집을 덮는 일을 막기 위해서다.

### 수동 — Settings의 [지금 동기화]

**조건 없이 서버 문서를 내려받는다.** 위 판정을 다시 태우지 않는다.

자동 경로와 다른 이유: 미전송 변경이 있는 기기가 "동기화"를 눌렀을 때 판정을 다시 태우면 오히려 *올려버린다*. 그러면 로컬이 낡은 쪽인 기기는 서버 것을 영영 못 받고, 버튼을 눌러도 화면이 그대로다. **버튼을 누른 것 자체가 의사표시**이므로 자동 경로의 보호 규칙을 여기까지 적용하지 않는다.

잃을 것이 있을 때만 — 즉 미전송 변경이 있을 때만 — 확인을 한 번 받는다. 확인하면 이 기기의 미전송 변경은 사라진다.

### 삭제는 어떻게 전파되나

푸시는 차이가 아니라 **문서 전체**를 보낸다. 그래서 삭제는 "새 문서에 그것이 없음"으로 전달되고, 채택하는 쪽은 통째로 갈아끼우므로 그대로 사라진다.

합집합 병합("서버에 있는데 로컬에 없는 것만 가져오기")을 하지 않는 이유가 이것이다. 그렇게 만들면 **지운 거래가 매번 되살아난다** — 서버에는 아직 있으니까. 삭제를 성립시키려면 문서 단위 last-write-wins여야 한다.

### 가져오기는 중복을 제거하지 않는다

풀은 교체이므로 중복이 생길 수 없지만, **CSV·JSON 가져오기는 병합이고 덧붙이기만 한다.**

- **CSV**: 행마다 새 id를 만든다. 같은 파일을 두 번 넣으면 두 배가 된다.
- **JSON**: id가 이미 있으면 건너뛰는 게 아니라 **새 id를 부여한다.** 역시 두 배가 된다.

같은 파일을 다시 넣기 전에 반드시 확인할 것. 한 번 들어가면 화면에서 눈으로 골라 지우는 수밖에 없다.

## 3. 코드 버전 동기화

데이터와 별개로, **기기가 어느 빌드를 돌고 있는가**도 어긋난다.

### 왜 필요한가

배포해도 폰이 옛 코드를 계속 돈다. 서비스 워커가 앱 껍데기를 precache하기 때문에 **네트워크 요청 없이 앱이 뜨고**, 새 버전이 나온 것을 알 계기가 없다.

브라우저는 `sw.js`를 다시 받아 설치된 것과 **바이트 단위로 비교**해 새 버전을 판정한다. 빌드마다 precache manifest의 해시가 바뀌므로 파일 바이트가 달라진다. 문제는 그 재요청이 **등록·내비게이션·`registration.update()`** 때만 일어난다는 것이다. 재개는 그 셋 중 아무것도 아니다.

### 언제 확인하나

| 계기 | 무엇 |
|---|---|
| 앱 로드 | 서비스 워커 등록 → 자동으로 바이트 비교 |
| 포그라운드 복귀 / bfcache 복원 | `registration.update()`를 직접 호출 |
| Settings 진입 | `/version.json`을 읽어 표시 |
| [업데이트] 버튼 | 확인 → 새 워커가 설치될 때까지 대기 → 교체 → 리로드 |

`registerType`이 `autoUpdate`이므로, 새 워커를 찾으면 묻지 않고 갈아끼우고 리로드한다.

### 버전은 커밋 해시

배포 주기가 없는 프로젝트에 semver를 붙일 이유가 없고, 해시는 돌고 있는 코드를 바로 가리킨다.

`vite.config.js`의 `define`이 `__APP_VERSION__`을 번들에 박는다. 값은 `WORKERS_CI_COMMIT_SHA` → `git rev-parse --short HEAD` → `"dev"` 순으로 정해진다. 같은 값이 `/version.json`으로도 나간다.

`dev`와 `test`는 배포본이 아니므로 "구버전"으로 판정하지 않는다. 개발 중에 가짜 업데이트 알림이 뜨지 않게 하기 위해서다.

### 배포 버전의 출처는 KV가 아니다

`/version.json`이라는 **정적 자산**에서 읽는다. KV에 버전을 기록하면 "마지막으로 쓴 **기기**의 버전"이 남을 뿐, 배포본 버전과 무관하다. 옛 코드로 도는 폰이 쓰면 KV엔 옛 버전이 남고, 새 코드로 도는 노트북이 그걸 읽어 자기가 낡았다고 판정하는 식으로 거꾸로 깨진다.

`.json`은 VitePWA 기본 `globPatterns`(js, css, html, ico, png, svg) 밖이라 precache되지 않는다. 그래서 이 요청은 실제로 네트워크에 도달하고, 답이 신선하다.

### Settings에 보이는 것

```
실행 중인 버전   a3d60ee
배포된 버전      a3d60ee
🟢 서버와 동기화됨
```

두 값이 다르면 [업데이트] 버튼이 뜬다. 배포된 버전을 읽지 못하면 이유를 이름으로 보여준다.

| 표시 | 의미 |
|---|---|
| 로그인 필요 | 로그인 페이지로 리다이렉트됨 |
| 배포본에 없음 | 리다이렉트 없이 HTML이 옴 — Worker의 SPA 폴백이 없는 자산을 대신 답한 것 |
| 서버 응답 없음 (404) | 응답은 왔으나 2xx가 아님. 코드가 실재 여부를 가른다 |
| 서버 응답 없음 | 요청이 완료되지도 못함 |
| 형식 오류 | JSON이지만 버전이 없음 |

### 내보낸 파일의 `appVersion`

JSON 내보내기에는 `appVersion`이 함께 실린다. **어느 빌드가 그 파일을 썼는지 추적하기 위한 것이며, 마이그레이션 게이트가 아니다.** 배포마다 바뀌므로 이 값으로 게이팅하면 과거 마이그레이션이 매번 다시 돈다. 스키마 판정은 `version`(= `SCHEMA_VERSION`)만 본다.
